# Stack

[Guidelines](https://jackhenry.design/pages/components/stack/)

<hr />

Stack is a layout primitive that layers the elements slotted into it on top of one another along the z-axis.
Every slotted element shares the same space, so they overlap instead of flowing in a row or column. Use it for overlays, badges anchored to a corner, or any UI where elements need to share the same space.

## When to use it

Reach for a stack when you need to overlap **independent, meaningful, non-blocking** elements and their source order already matches the order they should be read in. Good fits include:

- Caption or heading text over an image or media
- A value label centered on a chart or sparkline
- A duration or "LIVE" tag on a media thumbnail
- A skeleton placeholder over content while it loads

## When not to use it

Layering is purely visual — it carries no semantics — so some patterns are better solved another way:

- **A status or label that belongs to a component** — put it in that component's own flow (for example, a tag in a card's header slot). Reading order and association come for free, with no overlap risk.
- **Blocking interaction while loading or disabled** — this is a *state*, not a layout. Use `inert` (with `aria-busy`), a `disabled` control, or a native `<dialog>`; these also block keyboard and assistive tech, which `pointer-events` cannot.
- **Purely decorative layering** (gradients, watermarks) — a CSS `background`, pseudo-element, or single SVG never enters the accessibility tree.

Switching to `position: absolute` instead of a stack does not reduce any of these risks — it is the same visual layering with the same hazards. The safety comes from the semantics, not the positioning method.

## Usage

Import the `<forge-stack>` component:

```javascript
import '@jack-henry/jh-elements/components/stack/stack.js';
```

Place elements in the default slot. Each slotted element becomes its own layer, stacked in source order with the last element on top:

```html
<forge-stack>
  <img src="cover.jpg" alt="" />
  <span>Overlaid caption</span>
</forge-stack>
```

## Layering

Slotted elements stack in source order — the first element is the bottom layer and each following element sits above the previous one, so the **last** element renders on top. The stack sizes itself to its largest layer.

To control which layer is on top, reorder the elements in your markup. If the source order must stay as it is for reading order, set `z-index` on the layer that should be raised instead.

## Alignment

`alignment` sets where layers sit within the stack. By default it is `fill`, so each layer covers the whole stack. Any other value pins every layer to that edge or corner at its natural size:

      <td>Top edge: leading corner, centered, trailing corner</td>
    </tr>
    <tr>
      <td><code>leading</code>, <code>center</code>, <code>trailing</code></td>
      <td>Middle row: leading edge, centered, trailing edge</td>
    </tr>
    <tr>
      <td><code>bottom-leading</code>, <code>bottom</code>, <code>bottom-trailing</code></td>
      <td>Bottom edge: leading corner, centered, trailing corner</td>
    </tr>
  </tbody>
</table>

`leading` and `trailing` are the logical equivalents of left and right, so they follow the writing direction: in right-to-left languages, `top-trailing` is the top-left corner.

```html
<forge-stack alignment="top-trailing">
  <div class="avatar"></div>
  <jh-badge count="5" class="inset"></jh-badge>
</forge-stack>
```

### One alignment per stack

`alignment` applies to every layer in the stack, so a stack has a single anchor. You can't pin a badge to the top-trailing corner and a label to the bottom-leading corner in the same stack. Nest a stack inside a layer, or use two stacks, when you need more than one anchor.

Because every layer is aligned, any layer with an automatic size shrinks to its content when `alignment` is not `fill`. A base layer should be the largest layer or have an explicit size so it keeps its dimensions.

To span an edge, such as a caption bar along the bottom of an image, give the layer an explicit `width: 100%` and use `alignment="bottom"`.

### Anchoring inside or outside the corner

Alignment pins an element to an edge; to fine-tune where it sits relative to that edge, offset the element itself:

- Tuck it **inside** the corner with a `margin`.
- Make it **overhang** the corner with a `transform`.

```css
/* tucked inside the corner */
.inset { margin: var(--jh-dimension-200); }

/* hanging off the corner — the classic notification badge */
.overhang { transform: translate(50%, -50%); }
```

An overhanging element is clipped by any ancestor with `overflow: hidden`.

## Pointer events

Because layers overlap, a top layer sits over the ones beneath it and **intercepts pointer events across its whole area** — even where it looks transparent or empty. This means interactive elements on a lower layer (buttons, links, inputs) may not be clickable when a layer covers them.

When an upper layer is purely decorative, set `pointer-events: none` on it so clicks pass through to the layer below:

```css
.decorative-overlay {
  pointer-events: none;
}
```

## Overlays and loading states

A full-cover layer can dim content and block the mouse while something loads. But covering a layer does **not** remove it from the focus order or accessibility tree — users can still tab to and operate the controls beneath it. Because blocking is a state rather than a layout, pair the visual overlay with `inert` on the covered content (or disable its controls) and set `aria-busy="true"` on the region so assistive tech knows it is loading.

## Composition

Layout primitives are designed to compose. A `<forge-stack>` can hold `<forge-row>` and `<forge-column>` containers as layers (and vice versa), letting you arrange content within a layer while still stacking layers on the z-axis.

## Accessibility

The stack component contains no implicit accessibility features. 

### Author Guidance

- **Reading order follows source order.** Because the top layer must be *last* in the DOM to render on top, it is also read *last*. A visually prominent corner element — such as a status tag — is announced after the content it sits on. If it needs to be perceived earlier, associate it with ARIA rather than reordering the DOM; moving it earlier would drop it behind unless you also raise it with `z-index`.
- **Visually covered is not hidden from assistive tech.** Covered content stays in the focus order and accessibility tree. Use `inert` / `aria-hidden` (and `aria-busy` while loading) when a layer should truly block interaction — `pointer-events` only affects the mouse.
- **Anchor meaning to the right element.** For a badge on a control, fold the value into the control's accessible name (for example a button's `accessible-label`) and mark the visual badge `aria-hidden="true"` so it is not announced as a stray value.
- **ARIA references do not cross shadow boundaries.** `aria-describedby` and `aria-labelledby` only resolve within a single tree, so you can reference a sibling element but not something rendered inside another component's shadow root. Prefer putting meaningful status into a component's own content or accessible name.
